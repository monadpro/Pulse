# 攻击对比：普通 AMM 与 Pulse

页面底部的"攻击对比"区域，把**同一种攻击**分别打在普通 AMM 和 Pulse 上，直观地说明 Pulse 要解决什么问题、解决得怎么样。

> 一句话：在普通交易所里，谁排在前面谁占便宜；在 Pulse 里，同一个区块内所有人同一个价格，排在哪里都一样。

## 一、先看一下"三明治攻击"

假设你要买一些币：

1. 攻击者看到你的订单，**抢在你前面买入**，把价格推高；
2. 你的订单在**被推高后的价格**成交，买到的更少；
3. 攻击者**紧接着卖出**，赚走价格差。

你的订单被夹在攻击者的"买"和"卖"中间，像三明治，所以叫三明治攻击。它能成立的前提是：**攻击者能决定同一个区块里交易的先后顺序**（比如出块者本人，或者能买通出块者的人）。

## 二、两个交易场所

| | 普通 AMM | Pulse |
|---|---|---|
| 类型 | 自动做市商，一个币池，按 `x × y = k` 公式定价（类似 Uniswap），手续费 0.3% | 逐块统一价拍卖，每个区块一轮，同一批订单一起清算 |
| 价格怎么来 | 每笔交易**依次**推动价格，后面的人面对的是被前面的人改过的价格 | 一个区块里所有订单汇总成买卖曲线，算出**一个**价格，所有成交都按这个价 |
| 顺序重要吗 | **重要**：先买的人价格低 | **不重要**：同一个区块里先后无差别 |
| 代码 | `src/SimpleAMM.sol`，只用于这次对比 | `src/PulseExchange.sol` |

## 三、实验设定

所有币都是测试币。这些钱由一个叫 **AttackLab** 的合约持有，**不会用到你钱包里的 pMON 和 pUSD**，你只需要付手续费。

| 项目 | 设定 |
|---|---|
| AMM 池子 | 20,000 pMON 对 20,000 pUSD（初始价格 1.00） |
| 受害者 | 买入，出 1,000 pUSD |
| 攻击者 | 出 3,000 pUSD 做前置买入，之后全部卖回 |
| 攻击顺序 | 攻击者买入 → 受害者买入 → 攻击者卖出 |

## 四、结果

### 左边：普通 AMM

| 项目 | 数值 |
|---|---|
| 受害者本应买到（没有攻击时） | **949.66** pMON |
| 受害者实际买到 | **722.84** pMON |
| 受害者损失 | 少了 **23.88%** |
| 攻击者净赚 | **230.93** pUSD |

### 右边：Pulse

同样的攻击，AttackLab 在**同一笔交易**里提交 4 笔订单，所以它们落在同一个区块、同一个批次：

| 顺序 | 订单 |
|---|---|
| 1 | 普通流动性：卖出 20,000 pMON，最低价 1.00 |
| 2 | 攻击者前置：买入 3,000 pMON，最高价 1.13（很宽松） |
| 3 | 受害者：买入 1,000 pMON，最高价 1.13 |
| 4 | 攻击者后置：卖出 3,000 pMON，最低价 0.50 |

| 项目 | 数值 |
|---|---|
| 统一成交价 | **1.00** pUSD |
| 受害者买到 | **1,000** pMON，花 **1,000** pUSD，和没有攻击时一样 |
| 攻击者净利润 | **约 0**（链上算出是 -1 wei，页面显示为 0） |

### 为什么 Pulse 里攻击者赚不到

- 这个区块里所有成交都按**同一个价格**（1.00）。
- 攻击者先买 3,000，再卖 3,000，两次都按 1.00 成交，**一进一出刚好抵消**。
- 攻击者的前置订单**没有抢到更低的价格**，也**没有推高后面人的价格**，因为价格是由整个买卖曲线决定的，不是由先后顺序决定的。

## 五、页面上怎么用

1. 打开页面，**连接钱包**。需要有一点 MON 付手续费。
2. 点左边 **运行攻击**，在 MetaMask 里确认一次，约 1 秒后显示结果。
3. 点右边 **运行攻击**，确认一次，约几秒后显示结果。
   - 如果现场有自动清算脚本（keeper）在运行，它会自动清算，你只需要确认一次；
   - 没有的话，页面会再请你确认第二次，用于清算。
4. 对比两边的结果。

提示：
- **重复点左边，数字会略有变化**，因为 AMM 池子的状态每次攻击后都会改变，第一次的数字最标准。
- 每次点右边，keeper 会为清算和领取多花约 0.1 MON（keeper 有花费上限）。

## 六、是怎么实现的

| 合约 | 作用 |
|---|---|
| `SimpleAMM` | 一个极简的恒定乘积 AMM，包含 0.3% 手续费 |
| `AttackLab` | 扮演"能随意调整区块内顺序的恶意出块者"，按"攻击者买、受害者买、攻击者卖"的顺序，对两个场所各执行一遍 |
| `PulseExchange` | 被攻击的 Pulse 本体 |

**AMM 一侧**（`runAmm`，一笔交易完成）：
1. 先查询"没有攻击时受害者能买到多少"，记作基准；
2. 攻击者买入，受害者买入，攻击者把买到的全部卖出；
3. 攻击者利润 = 卖出所得 - 买入花费。

**Pulse 一侧**：
1. `runPulse`：一笔交易里依次提交 4 笔订单，保证在同一个区块；
2. 区块结束后清算（手动、或由 keeper 自动）；
3. `pulseReport`：读取结算结果，计算受害者实际花费，以及攻击者按清算价估值的净利润。

三个合约都已在 MonadVision 验证，地址见 [README](../README.md)。

## 七、这个对比能说明什么，不能说明什么

**能说明**：
- 在"攻击者可以决定同一个区块内交易顺序"的假设下，普通 AMM 的用户会被抬价，而 Pulse 里的顺序不产生收益。

**不能说明（请如实表述）**：
- **这是模拟，不是真实攻击**：是一个合约在扮演恶意出块者。Monad 本身没有全局 mempool，普通人很难这样操作；Pulse 是在应用层再加一层保护，两层互补。
- **Pulse 不能阻止所有价格操纵**：如果有人愿意拿真金白银的大额订单去改变整个买卖曲线，价格依然会变。区别是他自己的订单也按这个新价格成交，没法先低价买、再高价卖，没有"顺序套利"这个空子。
- **只有一个场景**：只展示了三明治攻击，没有覆盖其他形式的 MEV。
- **AMM 是简化版**：真实 AMM 有更多保护手段（比如滑点限制），这个对比里受害者没有设置。

## 八、可能被问到的问题

**Q：Monad 本来就没有全局 mempool，还会有这种攻击吗？**
A：local mempool 限制了谁能看到你的交易，这是网络层的保护。但负责出块的节点自己能决定顺序，所以应用层仍然需要不依赖顺序的机制。Monad 官方也在做排序者和验证者分离，方向一致。

**Q：用户为什么不直接设置滑点限制？**
A：滑点限制能限制损失上限，但仍然可以被攻击到上限，而且设置太紧会导致正常交易失败。Pulse 是从机制上让顺序不值钱。

**Q：这些数字是真的链上结果吗？**
A：是。AMM 和 Pulse 两边都在 Monad 测试网上执行，数字可以在 MonadVision 上核对，也可以用上面的测试命令复现。

## 九、30 秒讲解稿

"这是同一个攻击打在两个地方。左边是普通交易所：攻击者在我前面买、在我后面卖，我少买了将近四分之一，他白赚两百多。右边是 Pulse：同一个区块里所有人同一个价格，他的前置和后置订单抵消了，我按原价成交，他一分钱赚不到。不是靠监控或者黑名单，是机制本身让顺序失去了价值。"
